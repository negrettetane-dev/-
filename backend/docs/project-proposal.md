# “智途云枢”城市交通智能决策平台项目策划书

> 版本说明：本文早期内容以宁德单城市示范为背景；系统当前已升级为北京、厦门、福州三城通用型智慧交通控制中心，最新接口与实现以 `api-contract.md` 和代码为准。

## 一、项目名称

“智途云枢”城市交通智能决策平台

## 二、项目背景

随着城市机动车保有量持续增长，早晚高峰拥堵、突发交通事件、恶劣天气通行风险和园区通勤压力等问题日益突出。传统交通管理方式主要依赖人工巡查、固定监控和事后处置，存在响应速度慢、数据利用不足、预测能力弱等问题。

宁德作为新能源产业发展迅速的城市，重点园区、交通枢纽、商业中心和主城区之间的通勤需求明显增加。建设一个面向城市交通治理的智能决策平台，可以帮助管理者实时掌握交通态势，提前识别拥堵风险，优化出行路线，并为交通疏导和应急处置提供数据支撑。

本项目以福建宁德为示范城市，构建基于 FastAPI 的交通智能后端服务，提供交通态势汇总、路段状态分析、拥堵预测、路线推荐和事件预警等能力，为后续前端大屏、地图展示和多城市扩展奠定基础。

## 三、项目定位

本项目定位为面向城市交通治理场景的智能化服务平台。平台通过整合路段速度、车流量、天气因素和交通事件等多源数据，计算拥堵指数，预测未来交通压力，并向用户提供可视化展示和辅助决策接口。

项目当前阶段以 Demo 展示和课程/比赛成果为主要目标，优先保证系统结构清晰、接口稳定、功能完整、易于前后端协作。后续可逐步接入真实交通数据、天气 API、数据库和机器学习模型，升级为更完整的智慧交通应用。

## 四、项目目标

1. 建立宁德城市交通数据样例体系，覆盖主要道路、重点区域、交通事件和 POI 点位。
2. 实现交通态势汇总、路段状态、交通事件、拥堵趋势等基础接口。
3. 构建基于多源因素融合的拥堵指数计算方法。
4. 提供未来 60 分钟左右的拥堵预测能力，为提前疏导提供依据。
5. 提供最快路线、低拥堵路线、安全路线等多策略路径推荐。
6. 根据拥堵指数、天气风险和事件因素生成交通预警建议。
7. 保持接口规范统一，方便前端大屏、地图页面和预测页面快速对接。

## 五、目标用户

1. 交通管理部门：用于掌握城市道路运行状态，辅助交通疏导和事件处置。
2. 城市运行管理平台：用于接入智慧城市大屏，展示交通运行态势。
3. 普通出行用户：用于查看拥堵情况并选择更合适的出行路线。
4. 园区与企业管理方：用于分析通勤压力，提前发布错峰或绕行提示。
5. 比赛/课程评审对象：用于展示项目完整性、创新性和落地价值。

## 六、核心功能设计

### 1. 城市配置模块

提供城市基础配置能力，当前默认支持 `ningde`，后续可扩展至福建其他城市。该模块用于统一管理城市名称、行政区、重点道路、POI 点位和接口参数。

### 2. 交通态势模块

系统汇总城市交通运行情况，展示整体拥堵指数、平均速度、车流量、拥堵等级、路段分布和趋势变化。前端可基于该模块建设城市交通大屏首页。

### 3. 路段状态模块

系统对重点路段进行状态分析，输出道路名称、所在区域、经纬度折线、平均车速、车流量、天气影响、事件影响、拥堵指数和拥堵等级。该模块适合与地图结合，实现道路拥堵颜色渲染。

### 4. 交通事件模块

系统展示拥堵、天气、通勤压力等事件信息，包括事件类型、等级、所在区域、点位坐标和处置建议。该模块可用于事件列表、地图告警点和运营调度页面。

### 5. 拥堵预测模块

系统基于当前拥堵指数、趋势数据和规则模型，预测未来一段时间内的拥堵风险。当前版本采用规则模型，后续可接入历史交通数据并使用机器学习模型提升预测准确率。

### 6. 路径推荐模块

系统围绕起点和终点提供多策略路线建议，包括最快路线、低拥堵路线和安全路线。每条路线返回距离、预计时间、拥堵评分、安全评分、路线折线和出行建议。

### 7. 事件预警模块

系统根据拥堵指数、天气影响和突发事件因素生成预警信息，帮助管理人员提前发布绕行提示、加强路口疏导或提醒驾驶员降低车速。

## 七、技术方案

### 1. 后端框架

项目后端采用 FastAPI 框架开发，具备接口开发效率高、自动生成 API 文档、数据模型清晰、适合前后端分离等优点。

### 2. 数据模型

项目使用 Pydantic 定义接口数据结构，主要包括坐标、路段、交通事件、路线推荐等模型，保证接口返回数据格式稳定，便于前端调用。

### 3. 拥堵指数算法

当前版本采用规则融合算法，将平均速度、车流量、天气因素和事件因素进行加权计算，生成 0 到 100 的拥堵指数。指数越高，代表拥堵程度越严重。

拥堵等级可划分为：

- 0-35：畅通
- 35-60：缓行
- 60-80：拥堵
- 80-100：严重拥堵

### 4. 接口设计

系统提供 RESTful 风格接口，主要包括：

- `/api/cities`：城市配置
- `/api/traffic/summary`：交通态势汇总
- `/api/traffic/segments`：路段交通状态
- `/api/traffic/events`：交通事件
- `/api/traffic/trend`：拥堵趋势
- `/api/prediction/congestion`：拥堵预测
- `/api/route/recommend`：路线推荐
- `/api/warning/active`：活跃预警

### 5. 后续扩展

后续可引入 PostgreSQL 存储真实道路、事件和历史交通数据；使用 Pandas、Scikit-learn 或深度学习模型进行拥堵预测；使用 NetworkX、Dijkstra 或 A* 算法实现真实路网路径规划；通过 Docker Compose 实现一键部署。

## 八、项目创新点

1. 多源融合：综合速度、流量、天气和事件因素，而不是只依赖单一交通指标。
2. 预测预警结合：不仅展示当前状态，还尝试预测未来拥堵风险并生成预警建议。
3. 多策略路线推荐：同时考虑时间、拥堵和安全，为不同出行目标提供选择。
4. 面向城市扩展：接口设计保留城市参数，后续可以扩展到福建多城市。
5. 前后端解耦：后端提供标准接口，前端可独立建设大屏、地图和分析页面。

## 十二、风险分析与应对措施

### 1. 数据真实性不足

风险：当前阶段主要使用样例数据，可能与真实交通情况存在差距。

应对：先保证 Demo 逻辑完整，后续逐步接入公开天气 API、地图服务和真实历史交通数据。

### 2. 预测准确率有限

风险：规则模型难以适应复杂交通变化。

应对：后续引入历史样本数据，使用机器学习模型进行训练，并通过准确率、召回率等指标评估效果。

### 3. 前后端字段不一致

风险：前端展示依赖接口字段，字段变化可能影响页面渲染。

应对：维护 `api-contract.md` 接口契约，新增字段时保持向后兼容。

### 4. 多城市扩展复杂

风险：不同城市道路结构和数据来源不同，扩展时需要重新整理数据。

应对：保留统一城市参数和配置模块，将城市数据从代码逐步迁移到 JSON 或数据库。

### 5. 部署环境不稳定

风险：本地 Demo 可运行，但部署到服务器后可能出现端口、依赖或跨域问题。

应对：后续引入 Docker Compose，统一运行环境，降低部署难度。
